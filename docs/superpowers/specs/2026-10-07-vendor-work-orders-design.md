# 合作廠商工單設計

日期：2026-10-07，Asia/Taipei。狀態：已核准隔離原型實作；本機合成資料驗證，不是正式功能或已發布版本。
工作包：WO-PARTNERS-01（repository 內識別，不代表已建立 GitHub Issue）。
建議模型／速度：gpt-5.6-terra、medium。

## 1. 已確認需求與版本邊界

目標是讓房東依工作種類快速找到既有合作公司或個人，完成報價、派工與驗收。
工作分類為維修、清潔、其他工種；其他工種包含油漆、剪枝、除草，可填工種名稱。
允許多家公司及個人，每家公司多位接單／施工人員，不能綁死單一窗口。
依工作類別與物件設定第一、第二及後續優先順位，也允許手動指定。
維修及非固定價工作須報價核准；清潔或其他已有固定價約定的工作可直接派工。
同一套標準化核心、Workspace/RBAC，不按客戶建立客製功能分支。

此為 V3 隔離候選工作包，不新增功能到 V2.0/V2.1 正式運行流程。
使用者已同意隔離原型實作；本次不得擴大到正式產品整合。
不得將原型實作確認解讀成 Production 部署、Schema migration、建立 trigger、
修改 Properties／LINE／LIFF 或向真實廠商發訊息的授權。

## 2. 現況與隔離策略

現有 V2_REPAIR_TICKETS.js 保留房間／原房客／原租約快照及 append-only 事件，
房東訊息頁能更新五種報修狀態與公開回覆。它不是外部廠商身份或完整派工引擎。
新工單核心不直接擴充或改寫既有 V2 五種 status，不改帳單、押金、租約或排程。
第一階段本機使用持久化測試儲存與通知收件匣 adapter；不呼叫 Production API。
之後 staging 須獨立專案、資料與私有附件儲存，LINE 使用獨立測試 OA。
應先唯讀核對既有 OA/channel/webhook，再提出測試綁定，不修改正式 webhook。
所有實際部署目標需在計畫階段核實；缺少隔離綁定時只能本機驗證，禁止回落正式。
測試使用合成公司、個人、房間與附件，不複製房客證件或正式帳務。

未來接入報修入口以明確 adapter 匯入最小必要欄位，保留 source_repair_ticket_id
及来源 Workspace，不覆寫 V2 原紀錄；正式 adapter 啟用另需 Issue/授權。

## 3. 人員與合作對象

Partner 是公司或個人；PartnerMember 是可登入的窗口、派工管理者或施工者。
同一人可參與多個合作對象，但權限由伺服器驗證的 membership 決定。
WorkspacePartner 表示房東與合作對象的合作關係，含啟用狀態、工種、服務區域。
停止合作或停用人員會撤銷新操作／私有附件讀取；歷史事件不可刪除。
公司管理者可報價、拒絕邀請及接受固定價邀請，並在本公司已啟用成員中指定實際執行人；只有該受派管理者／施工者能開始施工、上傳附件及回報完工。公司窗口為唯讀；個人廠商可自行回覆並執行自己的派工。伺服器依已驗證 membership 決定角色，不採信瀏覽器送來的角色。跨公司轉包第一版不支援。
移除窗口後其他有權限成員可續接，施工／驗收事件保留當時 actor 快照。

「其他工種」的順位與固定價約定須保存並精確比對工種名稱；合作約定可記錄標題、起迄日、固定價及私有文件；不在此模組簽署法律合約。
固定价派工保存約定版本及價格快照，之後修改約定不會改既有派工價格。
公司不會因收到邀請而取得 Workspace 全部房客／房間／帳款權限。

## 4. 主要流程與狀態

工單狀態、邀請狀態、報價狀態分開管理，不以一欄混合多個廠商的回覆。

工單階段：draft → sourcing → awaiting_approval → assigned → in_progress
→ awaiting_acceptance → completed。取消為 cancelled；退回補修回 in_progress。
固定價工作從 sourcing 經明確指派／接單可到 assigned，不經 awaiting_approval。
房東確認派工本身即核准該固定價快照，不能因背景排程自動變成價格批准。

邀請：pending → sent → quoted／accepted／declined／expired／cancelled。
非固定價回覆是 quoted，不是施工接單；選中有效報價並核准後才產生 assignment。
固定價 accepted 可原子建立唯一 assignment。完工不等於驗收，也不自動結案。
廠商提供完工說明、照片及實際費用；房東驗收通過或註明原因退回補修。
實際費用超過核准價時須追加報價核准，未核准不能以超額值結案。
原核准報價、補價、完工回報、退回及最終驗收均保留完整版本與事件。
結案後不得改寫歷史；新發現的工作建立關聯的新工單。

## 5. 順位通知與防重

順位依 Workspace＋物件＋工種保存；同順位不允許兩個合作對象。
建立派工輪次時保存排序快照，後續調整設定不靜默重排已進行中的輪次。
預設順序邀請：先第一順位，拒接／逾期才通知下一順位。
房東可手動越級，亦可明確選擇同輪邀請多家報價；不默認廣播給全部廠商。
回覆期限於工單明確設定，第一版建議預填24小時（待計畫審閱可修改）；
記錄台北時區時間，急件以人工指定，不自動承諾到場 SLA。
已收到有效報價即等待房東決定，不因報價尚未核准繼續自動通知下一家。
有效报价被拒絕後，房東可選擇再走下一順位；過期邀请回覆不會復活派工資格。
已確定承接者後撤销其他未決邀請，停止後續通知。多人同時接單只有一位成功。
接單、核准、取消、逾時換順位需同一交易／短鎖重新驗證狀態與版本。
冪等鍵包含 Workspace、工單、輪次、合作對象與 action；同鍵不重複寫入。
廠商接單／完工提交可用權威讀回復原 timeout，不盲目再次提交。

## 6. LINE 與通知

登記 LINE ID 或電話不等於可自動 push。窗口／施工者透過邀請加入相應 OA，
完成伺服器驗證 LINE 身份與 membership 綁定；邀請不可單靠轉寄授予資料權限。
邀請使用短效一次性 token，伺服器存 hash；不可在 URL 帶 ID/access token 或私有資料。
正式多租戶用房東自己的 BYO LINE OA，不由共用 CMWebs OA 或個人 LINE 代發。
通知只含中性工單號／工種及登入連結，不在 LINE 訊息暴露租約、電話、門鎖密碼。
地址與已核准作業指引在登入且通過工單權限後顯示。
廠商可訂公司共用接單佇列與個人成員通知偏好；不把每位成員通知當成不同派工。

通知 outbox 與業務狀態在同一可復原交易中保存，交易提交後才由 worker 發送；
發送時不持有業務 ScriptLock，避免業務成功但通知事件遺失。
每個事件／收件人／channel 有唯一鍵，記錄 provider 狀態與嘗試次數。
明確未送達可重試；provider timeout 結果不明標為 delivery_unknown，
不可盲目自動重送；提供人工核對。通知停用仍留通知中心與工單紀錄。
本機 adapter 只寫測試收件匣，不取得真實 LINE token、不向外送出。

## 7. 資料與權限

建議持久化實體：partners、partner_memberships、workspace_partners、
partner_skills、priority_rules、service_agreements、work_orders、invitations、
quotes及quote_revisions、assignments、completion_reports、acceptances、
work_order_events、private_attachments、notification_outbox、idempotency_records。
所有作業列含 workspace_id；公司會員不因此取得其他 Workspace 工單。
工單可關聯物件、房間，或公共區域／戶外位置；非房間工作不填假 room_id／租約。
每筆事件含 actor、時間、from/to、版本與公開／內部可見範圍；事件 append-only。
業務主表與事件需在同一可復原提交邊界保存，不把事件成功當成主表寫入成功。
金額使用整數最小貨幣單位，預設TWD；包含稅費／材料／工資及合計，不能浮點失真。
报价有有效期限、預計工期及版本，核准固定某一版；改價生成新版本。

房東／團隊依 work_order_read、work_order_dispatch、work_order_approve、
work_order_accept 權限操作；供應商只依邀請及 assignment 操作自身工單。
API 每次由 server session解析 actor及Workspace，不信任 browser傳來權限標籤。
邀請階段僅公開工作摘要及必要區域；承接後提供房東核准的精確作業位置與指引。
廠商不能看其他家的報價、房客姓名／電話／租約、證件、銀行或押金資訊。
照片與PDF採私有儲存、短效授權下載，限制格式／大小，拒絕偽裝可執行檔；
上傳／下載均依工單權限。照片可能含個資，未核准不公開給房客或房源網站。
不得在 log、瀏覽器儲存、Git 放 LINE token、門鎖密碼或私有附件連結。
工單費用只作紀錄，不自動付款、扣押金、追加帳單或與財務資料同步。

## 8. 畫面與 API 責任

房東入口：工單總覽 → 建立工作／從報修關聯 → 選工種／優先合作對象 →
邀請或固定價派工 → 報價比較／核准 → 完工回報 → 驗收／補修。
合作對象頁管理公司／個人、多人會員、工種、物件順位及固定價約定。
外部工作台：我的邀請、報價、已承接工作、完工回報及已結案歷史。
手機優先，桌面同一核心；每一步顯示保存／待通知／通知失敗等真實狀態。
不把HTTP成功等同訊息收件或房東驗收成功。

API 分為 server-scoped合作对象/順位管理、工單建立/讀取、邀請、报价提交、
核准指派、接單、施工、完工、驗收、附件及通知讀回；寫入用POST、冪等與版本。
具體 routes／Schema／adapter 由後續實作計畫定義，不能先加到正式V2 dispatcher。

## 9. 實作順序與驗收門檻

第一個可運作切片：本機持久化合作对象＋工種順位、建立固定價清潔單、
邀請、接單、完工說明／私有合成照片、房東驗收；通知寫隔離收件匣。
第二切片：維修／其他工種报价版本與核准、逾時換順位、補價及退回補修。
第三切片：獨立 staging LINE綁定、通知adapter、真實授權測試帳號及照片驗收。
不可只做UI mock；每切片涵蓋儲存、API、權限、事件與結果讀回。

必測：多公司多人、停用成員、跨Workspace、越權工單／附件、其他報價不可見、
輪次順序／手動越級／已回報價等待核准、兩人競態接單、取消與逾時競態、
冪等重複提交、寫入中途失敗復原、通知成功／失敗／未知、完工不自動結案、
補修／超額核准、公共區域工作、固定價快照及既有V2完整回歸。
本機測試通過不等同 staging LINE收件／真機上傳／Production完成。
