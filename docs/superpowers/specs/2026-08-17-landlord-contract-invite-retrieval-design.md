# 房東發起合約邀請回查與重新產生設計

## 背景

房東建立 202 空房合約後，建立完成頁會顯示房客簽署 QR Code、邀請連結與一次性確認碼；離開頁面後，現有「合約申請管理」沒有穩定列出房東發起合約，且查詢失敗會被當成空清單，導致房東無法回查邀請。

## 目標

- 在既有「房東首頁 → 合約申請管理 → 房東發起合約」區塊列出待房客認領／簽署的合約。
- 提供查看邀請 QR Code、查看及複製邀請連結。
- 確認碼遺失時，允許房東重新產生邀請；舊邀請立即失效，新的邀請回傳新的 QR、連結與確認碼。
- 合約條件、房間、租約資料不因重新產生邀請而改變。
- 查詢或授權失敗時顯示明確錯誤，不得誤顯示為 0 筆。
- 房東首頁合約待處理數包含房東發起且尚待房客處理的合約。

## 不在本次範圍

- 不保存或回傳既有邀請的明文確認碼。
- 不改變房客認領、線上簽署、房東審核或合約生效規則。
- 不刪除既有合約、房間、帳單或付款資料。
- 不新增第三方電子簽章服務。

## 使用流程

1. 房東開啟「合約申請管理」。
2. 「房東發起合約」區塊列出 Workspace 內尚未取消、尚未完成且尚待房客處理的合約，例如房號 202。
3. 房東點選「查看 QR／邀請連結」，畫面顯示 QR、邀請連結、房間／租期摘要與確認碼狀態，並提供複製連結。
4. 若確認碼遺失，房東點選「重新產生邀請」並確認；系統取消舊邀請、建立新邀請，回傳新的 QR 對應連結與一次性確認碼。
5. 新邀請畫面提供「複製邀請連結」與可再次查看的 QR；離開後仍可回查新連結，但確認碼若再次遺失仍需重新產生。

## 後端設計

### 回查

沿用已驗證的房東 review session 與 Workspace read policy，修正 `landlord_contract_initiated_init` 的查詢與前端錯誤處理，使 `pending_tenant_signature`、`awaiting_tenant_signature` 等待房客處理狀態正確列出。

回查資料可包含：合約 ID、物件、房號、房客暫存資料、租期、租金、管理費、押金、邀請 ID、邀請狀態、到期時間與邀請 URL。不得包含確認碼雜湊或任何明文確認碼。

### 重新產生邀請

新增受已驗證房東 review session 保護的 `landlord_contract_invite_reissue` POST 操作：

- 驗證 Workspace、房東身分與 `contract_write` 權限。
- 僅允許處理該 Workspace 的房東發起、尚未完成且尚未被房客認領的邀請。
- 以 ScriptLock 序列化操作，避免同一合約產生多個有效邀請。
- 將舊邀請標記為 `cancelled`，保留稽核紀錄。
- 產生新邀請 ID、新確認碼雜湊與新到期時間，並更新合約的 `invite_id` 指標。
- 不改寫租約條件、合約內容、房間狀態或帳務資料。
- 僅在本次成功回應中回傳新確認碼、邀請 URL、邀請 ID、狀態與到期時間。

### 錯誤處理

前端需區分「查詢成功但沒有資料」與「授權、路由、Schema 或交換流程失敗」。後者顯示可操作的錯誤訊息與重新整理按鈕，不得靜默轉成空清單。

## 前端設計

- 保留現有合約申請管理頁與底部導覽。
- 房東發起合約清單每筆顯示房號、租期、房客狀態、邀請狀態與操作按鈕。
- 「查看 QR／邀請連結」使用同頁 modal，QR 由邀請 URL 產生；同時提供完整連結文字與複製按鈕。
- 「重新產生邀請」使用確認 modal，明確說明舊 QR／連結立即失效；成功後直接顯示新 QR、連結與確認碼。
- 首頁待處理數以後端回傳的房東發起待處理合約資料為來源，避免前端自行猜測狀態。
- 針對手機 LINE WebView 保留 safe-area、可滾動 modal、ARIA live 狀態與複製失敗的手動選取備援。

## 測試與驗證

- Apps Script 單元／runtime 測試：Workspace 隔離、權限、狀態篩選、重發原子性、舊邀請失效、新確認碼只在成功回應出現。
- UI 靜態測試：合約申請入口、QR modal、邀請連結複製、重新產生確認文案、錯誤不被轉成空清單。
- 回歸測試：既有房東發起新合約、續約、房客認領、房客簽署與房東審核流程。
- `node --check`、`git diff --check`、專案 validator 與受影響 Apps Script 測試。
- 部署後以唯讀探針確認正式 route 存在；不使用測試 UID 寫入正式房間或合約資料。

## 發佈與回復

- 在隔離 feature branch 實作，先部署 Apps Script 新版本，再部署 GitHub Pages。
- 使用既有正式 Web App URL，不更換前端固定入口。
- 若前端驗證失敗，可回復 Pages 到上一個 commit；若後端驗證失敗，回復 Apps Script serving deployment 到上一個已驗證版本。
- 不回復或刪除已存在的正式合約與邀請資料；重新產生邀請只會保留舊邀請為取消狀態。
