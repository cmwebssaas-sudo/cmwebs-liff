# 房東手動補登紙本合約設計

狀態：使用者已確認；本地候選已實作，尚未部署
日期：2026-09-03 (Asia/Taipei)
建議模型：`gpt-5.6-terra / medium`

## 目標

讓房東可以把已在現場完成簽署的紙本租約補進系統，特別是「房客已入住、
但當天沒有先建立系統資料」的情境，例如房號 202。補登完成後，該筆租約
直接成為系統可使用的有效租約，不再要求房客重新走線上簽署。

## 已確認的產品決策

以下決策來自使用者確認：

1. 紙本合約檔案必填，可上傳 PDF、JPG 或 PNG。
2. 身分證正面、身分證反面可先略過，之後從房客資料或合約文件入口補登。
3. 補登完成後直接建立有效／即將生效租約，不建立合約申請、不產生電子
     簽署邀請、不要求房客 LINE 簽署、不發 LINE。
4. 新房客與既有房客都適用，不限房號 202；房號 202 只是本次要處理的案例。
5. 原紙本合約日期、金額與紙本檔案需保存為當時快照；後續修改不得覆寫
   原紙本文件或已建立的租約版本。

## 使用流程

### 新房客／尚無系統房客資料

1. 房東從物件／房間選擇房號，按「手動補登紙本合約」。
2. 填寫房客基本資料、租期與費用條件。
3. 上傳已簽紙本合約檔案；身分證正反面欄位標示為選填。
4. 確認後，系統建立房客、使用者、有效租約與房間目前指向。
5. 成功頁顯示「紙本合約已補登」，並提供租約摘要與文件已保存狀態。

### 既有房客

1. 房東從房客詳細頁按「手動補登紙本合約」。
2. 房客姓名、手機、物件與房號預先帶入；房東可修正尚未保存的基本資料。
3. 填寫紙本租期與費用，並上傳紙本合約檔案。
4. 系統沿用既有房客 identity，不重建第二筆房客；新增一個紙本租約版本。

### 入口與流程簡化

- 新入口不使用 `V2_contract_requests`，也不導向合約申請紀錄。
- 新入口與 `landlord_contract_initiate_new` 分開；後者仍是需要房客線上
  認領、身分文件與簽署的電子流程。
- 房客端不增加任何補登操作；紙本補登是房東的主動操作。

## 表單欄位

### 必填

- 房號／房間。
- 房客姓名。
- 台灣手機號碼。
- 租約起始日。
- 租約結束日或租期月數（依既有新租表單規則，畫面只能有一種主要輸入方式）。
- 每月租金。
- 押金金額；押金月數可由金額反推或作為輔助顯示，不得造成兩個不同押金快照。
- 紙本簽約日。
- 已簽紙本合約檔案。

### 選填／可帶入預設

- 每月管理費。
- 付款日。
- 電費單價。
- 設備耗損費單價。
- 房客 Email。
- 身分證正面、身分證反面。
- 補登備註。

房間／Workspace 預設只在欄位沒有明確值時帶入；房東在畫面確認後的值由
後端重新驗證並保存，前端傳來的總額不可直接視為可信計算結果。

## 合約與房間狀態

- 租約起始日小於或等於台灣當日，且結束日尚未過期時，合約為 `active`，
  房間為 `occupied`，房客為可用狀態。
- 租約起始日在未來時，合約保存為既有系統支援的 `upcoming` 狀態；不提前
  顯示成目前有效租約，房間是否占用依既有 upcoming 規則處理。
- 結束日不得早於起始日；租期與日期需符合現有含首尾日規則。
- 同一 Workspace、同一房間不可存在重疊的有效／即將生效租約，也不可在
  同一補登請求重複建立。
- 既有合約、歷史合約、帳單與付款資料不覆寫。若房間目前已有有效合約，
  補登必須拒絕並要求房東先確認正確的續約或退房流程。

## 資料保存

### `V2_contracts`

沿用既有合約 canonical row 與現有欄位，不另建一套紙本合約表。補登合約
至少保存：

- 完整 Workspace、房東、房客、物件、房間關聯。
- 起訖日、租金、管理費、押金、付款日、電費與設備耗損費快照。
- `signing_mode = paper_backfill`，`contract_origin = paper_backfill`。
- `signed_at = paper_signed_at`；不偽造電子簽署時間、LINE identity 或電子
  簽名 artifact。
- `tenant_signing_submission_status = approved`，表示本筆不需要電子簽署且
  已由房東確認紙本文件；是否採用現有欄位需在實作前依 canonical schema
  驗證，不新增會讓既有 read model 誤判的狀態值。
- 紙本簽約日與補登操作人／時間；若現有 schema 沒有獨立紙本簽約日欄位，
  以 `signed_at` 保存紙本簽約日，將補登時間放入既有建立／更新 audit 欄位
  與備註。

不新增或偽造 `invite_id`、`tenant_signed_at`、LINE UID、電子簽名資料。

### `V2_contract_documents`

沿用既有私有 Drive 儲存與文件索引，將紙本檔案保存為：

- `document_type = legacy_contract`。
- `document_origin = paper_backfill`。
- 綁定同一 Workspace、`contract_id` 與 `tenant_id`。
- 保存檔名、MIME、大小、SHA-256、文件 ID、建立者與冪等鍵。

身分證文件若有上傳，使用既有 `identity_front`／`identity_back` 類型並綁定
同一租約；若未上傳，不阻止紙本租約成立，也不得建立空白或假文件紀錄。

### 房客／房間／檢視資料

- 新房客時建立既有 `V2_users`、`V2_tenants` 資料，沿用現有未綁定 LINE
  的房東代建模型；不把房東 LINE UID 寫成房客 LINE UID。
- 既有房客時沿用相同 `tenant_id`／`tenant_user_id`，只更新必要的基本資料
  與目前合約指向。
- 補登完成後更新 `V2_rooms.current_contract_id`、`current_tenant_id` 及
  既有房東／房客 view 所需指向；不得產生第二筆重複房客 view。
- 不自動建立帳單、不改動既有付款或欠款資料；後續帳務依有效租約與既有
  帳務週期建立。

## API 設計

新增一個受房東短期 review session 與 Workspace `contract_write` 權限保護
的 POST action：

### `landlord_contract_paper_backfill`

用途：在一次受保護操作中驗證並建立紙本補登租約。

請求包含房間、房客、租約費用、日期、紙本簽約日、紙本文件 Base64、文件
metadata、可選身分文件與 `idempotency_key`。`workspace_id`、`landlord_id`、
`tenant_id`、`room_id` 等 scope 由 server session／canonical row 決定或
重新驗證，不以 body 內容作為授權來源。

成功回應包含：

- 新建或沿用的 `tenant_id`。
- 新建 `contract_id`。
- `contract_status`、房間狀態與紙本文件保存摘要。
- 是否為相同冪等鍵的既有結果。

失敗回應必須明確區分：文件缺少、檔案格式／大小錯誤、日期錯誤、房間不存在、
房間已占用、租期重疊、跨 Workspace、權限不足與系統寫入失敗。

不新增任何邀請、簽署、房客詢問或 LINE 發送 route。

## 原子性、權限與安全

- 在既有合約 ScriptLock 內重新讀取房間、房客與合約 canonical rows，完成
  權限、Workspace、房間占用、租期重疊與冪等驗證。
- 所有必要驗證在寫入前完成；紙本檔案必須先通過 MIME、Base64、大小及私有
  Drive 設定驗證。
- 合約文件、合約 row、房客 row、房間 pointer、view row 需以固定順序寫入。
  任一寫入失敗時不得回傳成功；需執行可安全執行的補償清理，避免留下可被
  read model 當成有效租約的半筆資料。若外部 Drive 已成功但 Sheet 寫入失敗，
  必須標記／清理孤兒文件並保留錯誤 audit，不能把孤兒文件當成已補登成功。
- 不在持有既有 ScriptLock 時再取得同一把 lock；文件儲存 helper 必須支援
  由外層原子操作呼叫。
- `idempotency_key` 相同且請求內容相同時回傳原結果；相同 key 對不同內容
  必須拒絕，不可建立第二筆租約。
- 房東只能操作自己 session 所屬 Workspace 的房間、房客、合約與文件。
- 紙本文件維持私有 Drive，不回傳公開 URL，不把 Base64、Drive ID、身分證
  內容或秘密放入 URL、localStorage、console 或一般房客 read response。
- 不發 LINE、不建立電子邀請；操作紀錄仍要保留房東 user、membership、
  Workspace、時間與結果。

## 測試與驗收

新增 Phase 209 測試，至少覆蓋：

1. 房號 202 的新房客補登成功：建立房客、租約、紙本私有文件，合約依今日
   日期成為 `active`，房間指向新合約，且沒有 invite／LINE。
2. 既有房客補登沿用相同 tenant identity，不建立第二筆 tenant。
3. 缺少紙本文件、錯誤 MIME、超過 8MB、錯誤 Base64 時 fail closed，沒有
   合約或有效房間 pointer。
4. 身分證正反面缺少時仍可成功；有上傳時正確綁定文件類型。
5. 日期、金額、手機、房間占用、租期重疊與跨 Workspace 驗證。
6. 相同冪等鍵重送不增加 Sheet row、文件或邀請；不同 payload 使用相同 key
   被拒絕。
7. 寫入失敗不留下可見的半筆 active 租約，且既有合約與帳務資料不變。
8. UI 從房間與房客詳細頁都能進入補登入口；表單顯示紙本文件必填、身分證
   選填，且不顯示線上簽署邀請或合約申請步驟。
9. API 文件、測試矩陣、變更紀錄與專案 validator 同步通過。

## 不在本次範圍

- 不修改或刪除既有紙本／電子合約歷史資料。
- 不把紙本租約轉成電子簽署合約，不要求房客補簽。
- 不改退房結算、續約詢問、30 天條款或合約申請歷史頁的既有資料。
- 不自動補建立過去月份帳單，不自動變更付款狀態或押金收支。
- 不執行 Production Sheet migration、Apps Script deploy、GitHub Pages
  publish、LINE 操作或真實房東交易；完成候選版後另行取得部署授權。

## 待審閱的實作界線

實作前需以目前 canonical schema 驗證欄位是否完整；若發現紙本來源或 audit
欄位不足，優先採 additive-only header guard，不刪除或改名既有欄位。若現有
資料結構無法在不破壞既有 read model 的前提下表示 `paper_backfill`，則先
停止寫入並回報具體 schema blocker，不以任意字串偽裝成電子簽署狀態。
