# CMWebs 房間報修工單歷史與房客個資隔離設計

**狀態：** 已完成初版，待使用者審閱；Gate 0 前不進入實作

**日期：** 2026-09-15（Asia/Taipei）

## 1. 目標

建立以房間為主體的報修工單歷史。房間換房客後，既有報修紀錄、處理狀態與
維修結果仍然保留，房東與授權管理團隊可以查看完整生命週期；現任房客則不
得看到前房客的個資、對話或附件。

本設計沿用現有房客訊息／報修入口與 Workspace、角色權限，不在本階段重寫
登入、通知或帳務流程。

## 2. 已確認的產品決策

- 報修歷史的永久主體是 `workspace_id + room_id`，不是房客。
- 每張工單保留建立當下的房客與租約關聯，作為歷史與責任判定依據；換房客
  不會覆寫原房客資料。
- 未結工單在換房客後仍留在房間的房東／管理團隊待辦清單。
- 前房客造成的損壞、押金扣款或賠償，必須連結原房客與原租約，不得自動
  歸責給現任房客。
- 房東及有權限的管理團隊可查看完整工單歷史；房客只能查看自己的工單。
- 現任房客若需要知道房屋有維修，不顯示前房客身分，只顯示最小必要的
  房屋維修資訊，例如項目、日期與目前狀態。
- 前房客姓名、電話、Email、LINE User ID、訊息內容、個人附件及其可識別
  的照片，均不得出現在現任房客 API 回應或畫面。

## 3. 現況與整合邊界

目前 `V2_tenant_messages` 已保存房客訊息／報修基礎資料，包含
`tenant_id`、`tenant_user_id`、`tenant_line_user_id`、`tenant_name`、
`room_id`、`room_name`、`message_category` 與 `status`。既有房客送出
`repair` 類型時會建立訊息紀錄並通知管理團隊。

第一階段應保留既有 `V2_tenant_messages` 作為相容的報修入口與既有訊息來源。
報修工單的完整狀態歷史另採附加的 append-only 事件紀錄，避免把一般訊息、
報修工單與歷史狀態混成只能保留最後狀態的一列。

本設計不直接改動正式 Apps Script、Google Sheets 或 GitHub Pages；待 Gate 0
完成並取得實作授權後，才建立 migration、API 與 UI 變更。

## 4. 建議資料模型

### 4.1 工單主資料

可以沿用既有 `message_id` 作為初始工單的相容來源；實作完整工單模組時，
新增 `repair_ticket_id` 或等價的穩定工單識別碼，並保留原始 `message_id`。
工單至少需要以下欄位：

| 欄位 | 用途 |
| --- | --- |
| `workspace_id` | Workspace 隔離主鍵 |
| `repair_ticket_id` | 工單穩定識別碼 |
| `message_id` | 對應原始房客報修訊息 |
| `property_id` | 物件關聯 |
| `room_id` | 房間生命週期主鍵 |
| `room_name_snapshot` | 建立時房號／名稱快照 |
| `tenant_id` | 建立當下房客，僅供授權後台與稽核使用 |
| `lease_id` | 建立當下租約，供責任、押金或賠償關聯 |
| `tenant_name_snapshot` | 房東後台歷史辨識；不得進入其他房客 API |
| `category` | 報修類型 |
| `title` / `description` | 問題描述 |
| `priority` | 一般／急件 |
| `status` | 待處理、處理中、待確認、已完成、已關閉 |
| `responsibility_party` | 房東、房客、公共設備或待判定 |
| `estimated_cost` / `actual_cost` | 維修費用；不直接等同押金扣款 |
| `created_at` / `closed_at` | 工單時間 |

`tenant_name_snapshot`、原始 LINE ID 與附件索引屬於後台受保護資料。資料表
中的保存不代表可以直接回傳給房客；所有房客讀取都必須經過授權後的安全
projection。

### 4.2 工單事件紀錄

新增的事件資料應採 append-only：

| 欄位 | 用途 |
| --- | --- |
| `workspace_id` | Workspace 隔離 |
| `repair_ticket_id` | 工單關聯 |
| `event_id` | 事件識別碼 |
| `event_type` | 建立、狀態變更、回覆、指派、費用更新、關閉 |
| `from_status` / `to_status` | 狀態變更前後 |
| `actor_type` / `actor_id` | 房客、房東、團隊成員或系統 |
| `internal_note` | 後台內部備註，不進房客 projection |
| `public_note` | 可選的房客可見說明，不含個資 |
| `created_at` | 事件時間 |

不得用換房客時的資料更新去改寫既有事件；新的租約只會影響目前房間狀態與
新的工單權限範圍。

## 5. 換房客時的規則

### 5.1 房東／管理團隊視角

- 以房間查詢時，顯示該房間完整工單歷史。
- 未結工單標示「建立於前租約」或「目前房客」，協助管理團隊判斷責任。
- 原房客與原租約資訊依 Workspace／角色權限顯示。
- 工單完成後仍不可刪除或移到新房客名下；如需更正，新增稽核事件。

### 5.2 房客視角

- 房客 API 先由伺服器以目前已驗證的 `tenant_id`、`workspace_id`、`room_id`
  篩選，再組合回應；不可先回傳全房間資料再由前端過濾。
- 預設只回傳目前房客自己建立的工單與事件。
- 若產品決定顯示房屋維修摘要，只能回傳去識別化欄位：維修項目、建立／完成
  日期、狀態與不含個資的公共說明。
- 不回傳前房客姓名、聯絡方式、LINE ID、原始訊息、內部備註、個人照片、
  附件原始檔名或可推回身分的 URL。
- 房客不能以修改 query string、`room_id`、`tenant_id` 或工單 ID 取得其他
  房客資料；每個讀取路由都必須重新驗證目前登入身份與 Workspace 關聯。

### 5.3 附件與照片

維修照片可能包含房客個人物品、文件或身分資訊，因此不能只依賴工單文字
欄位過濾。附件要有獨立的可見範圍：

- 房東／授權團隊：依工單權限查看。
- 工單建立者：可查看自己上傳的附件。
- 現任房客：不可查看前房客附件；若需顯示房屋維修結果，建立不含個資的
  公開維修附件或摘要後再提供。
- 下載 URL 必須是短效、伺服器授權產生的 URL，不把 Drive ID 或永久公開 URL
  放到房客回應。

## 6. 權限與 API 邊界

後續實作至少需要分開三種讀取 projection：

1. **Landlord repair admin projection**：完整房間歷史、責任關聯、成本與
   房客／租約快照，受 Workspace 與角色權限保護。
2. **Tenant own-ticket projection**：目前房客自己的工單與可見事件。
3. **Tenant room-maintenance summary projection**：只有在產品需要時啟用，
   僅含去識別化房屋維修狀態。

不能讓房客直接呼叫房東的工單初始化路由，也不能使用「把 tenant_name
移除」作為唯一防護；查詢集合本身就必須只包含授權範圍。

新增或變更 API 時，才同步更新 `docs/04-API-ROUTES.md` 與測試；正式路由名稱
在實作前不先視為已存在。

## 7. UI 規格

### 房東後台

- 房間詳情新增「報修紀錄」時間軸。
- 工單卡顯示房號、項目、優先程度、狀態、建立時房客／租約與處理成本。
- 換房客後，未結工單置頂並標示原租約，不自動改成新房客責任。
- 需要押金扣款時，提供「連結原租約結算」操作，不能直接從目前房客頁面
  推導責任。

### 房客端

- 顯示「我的報修」與每張工單的處理進度。
- 房屋公共維修摘要若啟用，使用「房屋維修紀錄」名稱，不顯示前房客資訊。
- 內部備註、責任判定、費用談判與前房客內容不渲染。

## 8. 遷移與相容性

- 既有 `V2_tenant_messages` 中 `message_category=repair` 的資料不得刪除。
- 可以用既有 `message_id` 建立初始工單映射；缺少 `room_id` 的歷史資料不得
  猜測房間，應標記待人工整理。
- 舊工單的 `tenant_id`、`tenant_name` 與原始內容只供後台相容讀取，不能因
  新房客入住而更新成新房客。
- 所有新增欄位採 append-only；不重排、不刪除既有欄位。
- 遷移完成前，舊訊息頁與新報修頁若同時存在，必須以 `message_id` 去重，
  避免同一報修在畫面上出現兩張可操作工單。

## 9. 驗收條件

- 房客 A 建立報修後，房客 A 換租／房客 B 入住，工單仍可由房東在該房間歷史中
  查到。
- 房東可以看到 A 的原租約關聯；房客 B 的 API 與 UI 看不到 A 的姓名、電話、
  Email、LINE ID、訊息、內部備註與附件。
- 房客 B 嘗試替換 `tenant_id`、`room_id` 或工單 ID 時，伺服器回傳拒絕或空集合，
  不洩漏資料存在與否以外的內容。
- 房客 B 只能看自己的工單；若啟用房屋摘要，摘要不含可識別前房客的欄位。
- 前房客造成的費用仍連結 A 的 `tenant_id + lease_id`，不會在新租約中自動
  變成 B 的責任。
- 工單狀態每次變更都有 append-only 事件與操作者稽核紀錄。
- `npm run validate`、完整 Node 測試、受影響 Apps Script 測試與
  `git diff --check` 通過；真實房客／房東身份與正式資料驗收標記
  `HUMAN_REQUIRED`，不以靜態測試代替。

## 10. 風險與回滾

- 最大風險是把整個房間工單資料直接回傳給房客，再嘗試於前端隱藏。實作必須
  先做伺服器端 projection 與授權測試。
- 若新增工單模型造成既有訊息重複，保留 `message_id` 相容關聯並關閉其中一個
  可操作入口，不刪除歷史資料。
- 若房客 projection 發生越權，立即停用房客房屋摘要路由，保留房東後台工單
  讀取，並回滾新增的房客 API／UI；不回滾或刪除原始報修資料。
- 本設計不授權 Production deployment、Apps Script 寫入、Google Sheets migration
  或 LINE 發送；這些動作需另行取得授權並依 release gate 執行。
