## Root cause

The backend correctly rejects authenticated GET requests. The local Phase 95.2
frontend uses `staging-secure-api.js`, obtains `liff.getIDToken()`, and submits
an iframe form with HTTP POST. The deployed staging hosting revision is older:

- all six deployed tenant-page SHA-256 values differ from the reviewed local
  Phase 95.2 files;
- `staging-secure-api.js` returns HTTP **404**;
- the hosted tenant binding page still invokes the legacy JSONP/GET path;
- the new backend therefore fails closed with `AUTH_POST_REQUIRED` before LINE
  token verification.

This is a release-artifact mismatch, not a LINE token verification logic
failure and not a Spreadsheet schema failure.

## Remaining blockers

1. Deploy the exact reviewed Phase 95.2 staging frontend artifact, including
   `staging-secure-api.js`, without changing Production hosting.
2. Reconfirm the six page hashes and secure bridge hash against the release
   manifest.
3. Repeat real tenant and landlord LIFF flows and prove successful ID-token
   verification.
4. Execute invalid, expired, wrong-audience and provider-unavailable token
   cases without exposing token contents.
5. Complete role-negative tests for viewer, maintenance, manager and finance
   using disposable staging memberships; Phase 95.3 directly proved only the
   canonical landlord and cross-Workspace boundary remotely.
6. Prove notification stale-processing recovery on the remote staging trigger
   without duplicate LINE delivery.
7. Regenerate the Production SHA manifest after the matching frontend staging
   deployment and obtain named human approval plus a Production rollback
   version.
