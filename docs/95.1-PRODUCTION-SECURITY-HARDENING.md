# Phase 95.1 — Production Security Hardening

## Scope and status

This phase changes only `release/staging/`. Production Apps Script, frontend,
Spreadsheet, Script Properties, LIFF and deployments remain untouched.

**Local implementation status: COMPLETE**  
**Production readiness status: CONDITIONAL NO-GO pending staging deployment and real LIFF/RBAC/rollback verification**

## 1. Server-verified LINE identity

New module: `V2_LINE_IDENTITY_SECURITY.js`.

Security boundary:

1. The staging frontend obtains the raw ID token using `liff.getIDToken()`.
2. It submits the token in an HTTPS POST body through the existing iframe
   bridge; UID and token are not included in the query URL.
3. Apps Script sends the token and configured LINE Login channel ID to
   `POST https://api.line.me/oauth2/v2.1/verify`.
4. Only the verified `sub` claim becomes the runtime LINE UID.
5. `line_user_id` supplied by the client is ignored.
6. GET API authentication fails closed with `AUTH_POST_REQUIRED`.
7. Invalid/expired/wrong-audience tokens fail closed without logging tokens.

Required Script Property:

- `CMWEBS_LINE_LOGIN_CHANNEL_ID`

Optional test identity is server-owned and disabled by default. It requires
both `CMWEBS_FEATURE_ALLOW_TEST_IDENTITY=true` and
`TEST_TENANT_LINE_UID`; the caller cannot provide the UID.

Official design references:

- https://developers.line.biz/en/docs/liff/using-user-profile/
- https://developers.line.biz/en/reference/line-login/#verify-id-token

## 2. Central RBAC permission layer

New module: `V2_RBAC.js`.

Every one of the 71 staging `landlord_*` routes now has an explicit policy.
Routes missing from the policy map fail closed with `RBAC_POLICY_MISSING`.

Principal boundaries:

| Principal | Boundary |
|---|---|
| Tenant | Verified LINE subject; tenant resolver restricts data to that identity |
| Landlord candidate | Authenticated entry/registration/invitation routes only |
| Workspace member | Active user, Workspace and membership required |

Policies:

- `workspace_read`
- `team_manage`
- `settings_write`
- `operations_write`
- `message_write`
- `payment_write`
- `contract_write`
- `payment_and_terminate`
- `delete_data`

Financial and termination actions require permission flags instead of merely
an active membership. Repair operations allow the maintenance role, while
contract and payment operations remain denied to maintenance/viewer roles.

## 3. Environment configuration and feature flags

Phase 91–94 runtime no longer checks for the literal `staging` environment.
Runtime availability is controlled by environment configuration and explicit,
fail-closed feature flags:

- `CMWEBS_FEATURE_NOTIFICATION_QUEUE`
- `CMWEBS_FEATURE_REPAIR_WORKFLOW`
- `CMWEBS_FEATURE_LEASE_LIFECYCLE`
- `CMWEBS_FEATURE_BILLING_LIFECYCLE`
- `CMWEBS_FEATURE_MOVE_OUT_SETTLEMENT`
- `CMWEBS_FEATURE_SCHEMA_MIGRATIONS`
- `CMWEBS_FEATURE_ALLOW_TEST_IDENTITY`

`CMWEBS_ENVIRONMENT` remains mandatory. Feature values accept only explicit
`1`, `true`, `enabled`, or `on` values. Missing flags are disabled.

## 4. Deposit settlement transaction safety

New module and Sheet schema: `V2_SETTLEMENT_TRANSACTION.js` /
`V2_SETTLEMENT_LEDGER`.

Ledger fields:

- `ledger_id`
- `idempotency_key`
- `operation`
- `status`
- `created_at`, `updated_at`
- `workspace_id`, `actor_user_id`
- `request_id`, `settlement_id`
- `before_json`, `result_json`
- `error_code`, `error_message`
- `committed_at`, `rolled_back_at`

Safety behavior:

- settlement preparation and refund confirmation require an 8–128 character
  idempotency key;
- a project-wide `ScriptLock` serializes settlement mutations;
- committed calls replay their stored result without repeating writes;
- duplicate/non-committed keys fail closed;
- affected existing rows and append boundaries are captured before mutation;
- returned failures or exceptions restore captured rows and appended rows;
- the ledger records `processing`, `committed`, `rolled_back`, or
  `rollback_failed` evidence;
- runtime settlement operations fail closed when the ledger is missing or its
  schema is incomplete; only the feature-gated schema migration may create or
  extend the ledger;
- `V2_DEPOSIT_SETTLEMENTS` records its `idempotency_key`.

Route additions are not required. Existing Phase 94 write routes add the
`idempotency_key` parameter:

- `landlord_move_out_inspection_complete`
- `landlord_deposit_refund_confirm`

## Remaining risks

1. The secure POST bridge and LINE token verification require a real staging
   LIFF smoke test after deployment.
2. The new Script Properties and feature flags have not been configured in the
   remote staging project in this phase.
3. The settlement ledger migration has not been run remotely.
4. Role tests are isolated fixtures; a disposable real Workspace role matrix
   test is still required.
5. LINE verification adds an external network dependency and latency; failure,
   timeout and rate-limit behavior must be measured in staging.
6. Settlement rollback uses compensating Sheet writes. All future writers of
   the same rows must follow the same global locking contract.
7. Notification stale-`processing` recovery and the existing missing local
   hosting artifact from Phase 95 remain separate release blockers.
